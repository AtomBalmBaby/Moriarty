## Providers

Provider setup is documented at [docs.twinny.dev](https://docs.twinny.dev/providers/overview/), one page per server:

- [Ollama](https://docs.twinny.dev/providers/ollama/)
- [LM Studio](https://docs.twinny.dev/providers/lm-studio/)
- [llama.cpp](https://docs.twinny.dev/providers/llama-cpp/)
- [Other local servers](https://docs.twinny.dev/providers/other-local-servers/) (Open WebUI, LiteLLM, text-generation-webui, QVAC, any OpenAI-compatible server)
- [Hosted APIs](https://docs.twinny.dev/providers/hosted-apis/)
- [Devices (P2P)](https://docs.twinny.dev/providers/devices/)
- [A team gateway](https://docs.twinny.dev/teams/connect/)

Which models suit completion, chat and embeddings, and which fill-in-the-middle template each uses, is on [Supported models](https://docs.twinny.dev/providers/supported-models/).

### Inference request tracing

With Twinny logging enabled, inference events include client-generated `operation_id`, `request_id`, and attempt identifiers. Direct `fetch` transports emit `http_attempt` events per HTTP request; TokenJS emits `provider_attempt` events per SDK invocation. Agent requests also record the tool-loop step and configured step limit. These IDs are generated by Twinny and are not llama.cpp task IDs.

The configured llama.cpp endpoint and the settings in VS Code do not identify the server build or prove that it exposes its internal task ID. Twinny records a `server_task_id` only when an explicit `x-llama-task-id` response header or `server_task_id`/`llama_task_id` stream field is returned. An ambiguous `task_id` field or `x-task-id` header is recorded only as an unconfirmed candidate. No client-supplied correlation header is sent because support by the target llama.cpp version cannot be established here.

If the server does not expose a task ID, correlate Twinny's `http_attempt.dispatched` timestamp, endpoint, model, and lifecycle with llama.cpp request logs using synchronized clocks. That timestamp/ordering match is an inference, not proof that a particular server task ID belongs to a Twinny request. TokenJS manages its own HTTP transport; its attempt ID identifies the Twinny SDK invocation, not an individual internal HTTP retry, and those hidden retries cannot be correlated from Twinny.
